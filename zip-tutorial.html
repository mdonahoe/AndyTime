The Big Picture

ZIP files use the DEFLATE algorithm, a two-stage pipeline:

Stage 1 — LZ77: Scans the input for repeated byte sequences and replaces them with compact back-references: a (length, distance) pair that says "copy N bytes from M bytes ago." The more repetition in your data, the bigger the win.

Stage 2 — Huffman coding: Assigns shorter bit-codes to more frequent symbols. The letter e might need only 3 bits; a rare byte like 0x7E might need 12. On average, this beats the fixed 8 bits per byte used by raw ASCII.

The simulator below focuses on LZ77 using a simplified fixed-width byte format so each output byte maps cleanly to its input source. Tap any output byte to trace it back.

Stage 1: LZ77 — Eliminating Repetition

LZ77 maintains a sliding window of recently-seen bytes. At each position it looks backward to find the longest sequence that already appeared in the window.

Example: "abcabcabc"

// Position 0-2: nothing in window yet → output literals Literal 'a' Literal 'b' Literal 'c' // Position 3: window holds "abc", and input[3..8] = "abcabc" // Found match at dist=3, len=6 — the whole "abcabc" repeats! BackRef(len=6, dist=3) // Total: 3 literals + 1 back-reference (vs 9 raw bytes)

Overlapping references

The decoder reconstructs output left-to-right, so a back-reference can point to bytes it's still writing. This lets a single reference expand into a long run:

// Input: "aaaaaaa" (7 a's) Literal 'a' BackRef(len=6, dist=1) // Decoder: write 'a', then copy 6 bytes from 1 position back // Each copy step reads the 'a' just written → "aaaaaaa" ✓

Minimum match length

In our simplified format a back-reference costs 4 bytes (flag + length + 2× distance), so we only emit one when the match is at least 3 bytes — otherwise a literal is cheaper. Real DEFLATE uses a 3-byte minimum for the same reason.

Stage 2: Huffman Coding

After LZ77 we have a stream of symbols (literals and length/distance pairs). Huffman coding replaces each symbol with a variable-length bit string: short codes for frequent symbols, longer codes for rare ones.

// Frequency analysis of "aababc": 'a' × 3 → code: 0 (1 bit) 'b' × 2 → code: 10 (2 bits) 'c' × 1 → code: 11 (2 bits) // Original: 6 chars × 8 bits = 48 bits // Huffman: (3×1) + (2×2) + (1×2) = 9 bits

The Huffman tree is stored at the start of each compressed block so the decoder can reconstruct it. In practice DEFLATE uses two trees: one for literals/lengths and one for distances.

The simulator below skips Huffman coding and uses fixed-width bytes (1 byte per literal, 4 bytes per back-reference). This makes every output byte map 1-to-1 to a token, so you can trace provenance clearly. The LZ77 back-reference structure is identical to what real DEFLATE uses — only the bit-packing layer is simplified.

ZIP File Structure

A ZIP file is a container for multiple compressed entries. Each entry has this layout on disk:

SectionSizeDescription
Local file header30 + n bytesSignature PK\x03\x04, filename, compression method, CRC-32, uncompressed & compressed sizes
File datavariableDEFLATE-compressed content — this is what the simulator shows
Data descriptor0 or 16 bytesOptional: written when sizes are unknown at write time (streaming archives)
… repeat for each file …
Central directoryvariableOne record per file, with filename + offset into archive. Lets you seek to any file without scanning everything.
End of central dir22 + n bytesSignature PK\x05\x06, entry count, offset of central directory. Always at the very end.

Why is the index at the end?

ZIP was designed for appending: you write each file's data, then write the central directory at the end. To add a file you write the new entry then rewrite the central directory. Readers find it by scanning backwards from the last 22 bytes.

The "PK" magic number

ZIP files begin with PK — the initials of Phil Katz, who created the format in 1989. His company PKware published the DEFLATE spec, which later became the basis for gzip, zlib, PNG image compression, and HTTP's Content-Encoding: gzip.

Other formats using DEFLATE: gzip (.gz) — single-file wrapper with a checksum header; zlib — compact stream format used inside PNG, HTTP, PDF; jar — ZIP with a Java manifest; docx / xlsx / pptx — ZIP archives containing XML files.
